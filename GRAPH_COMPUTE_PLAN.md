# Graph as Compute — Implementation Plan

**Date**: April 11, 2026  
**Status**: Planning — not yet started  
**Based on**: `erp_dag_framework_surrealdb.md` + existing `spotledger-architecture.md`

---

## The Core Shift

**Before:** Rust `save_proxy` is the orchestrator. It calls `UPSERT` and trusts `DEFINE EVENT` for side-effects.

**After:** `fn::pipeline::run($doc_id, $doctype, $action)` **is** the orchestrator. Rust's save handler becomes a one-line proxy that calls it. The pipeline graph, validation logic, computation, GL posting, cancellation cascade — all live as SurrealDB records and `fn::` functions. Rust retains exactly two responsibilities: **auth** and **naming**. Nothing else.

---

## Layer Responsibilities After Migration

| Layer | Before | After |
|-------|--------|-------|
| **Rust `save_proxy`** | Auth + UPSERT | Auth + Naming + `fn::pipeline::run(...)` call |
| **Rust `hooks.rs`** | In-process `HookFn` dispatch table | Deleted for runtime types. Events live in SurrealDB. |
| **SurrealDB** | `DEFINE EVENT` + `DEFINE FIELD ASSERT` | All of the above **plus** pipeline graph topology, domain functions, cascade rules, execution log |
| **WASM plugins** | Schema seed + complex hooks via Extism | Schema seed + optionally heavy compute. Wiring `.surql` files ship with the app. |

---

## Wiring Is Data, Functions Are Code

This distinction drives the entire architecture:

| Artifact | Nature | File? | Mutable post-install? |
|----------|--------|-------|-----------------------|
| `fn::` domain functions | Code | Yes — always | Via `DEFINE FUNCTION OVERWRITE` at upgrade |
| `registry.surql` | Generated code | Generated at install | Regenerated when functions change |
| `doctype_meta` records | Data | Seed from Rust codegen | Yes — freely |
| `pipeline_stage` records | Data | Seed from Rust codegen | Yes — AI can add/remove |
| `pipeline_node` records | Data | Seed from Rust codegen | Yes — AI can add/remove |
| `has_node` edges | Data | Seed from Rust codegen | Yes — AI rewires freely |
| `cascade_rule` records | Data | Seed from Rust codegen | Yes — AI can change cascade paths |

**No per-doctype wiring files.** The wiring (stages, nodes, edges) is generated at install time by Rust code that reads DocType JSON. It represents factory defaults. After first install, the live SurrealDB graph is truth — it diverges as AI or admins mutate it. Re-running `install-app` regenerates functions but never clobbers live wiring.

**No `meta.surql` or `wiring.surql` per doctype.** Those are generated by Rust.

`registry.surql` is **never hand-edited** — generated from scanning the above files.

### 1.2 — Framework Schema (`framework/schema.surql`)

```surql
-- Doctype registration
DEFINE TABLE doctype_meta SCHEMAFULL;
DEFINE FIELD name            ON doctype_meta TYPE string;
DEFINE FIELD is_submittable  ON doctype_meta TYPE bool;

-- Pipeline stages (one per doctype+action+phase)
DEFINE TABLE pipeline_stage SCHEMAFULL;
DEFINE FIELD name     ON pipeline_stage TYPE string;
DEFINE FIELD order    ON pipeline_stage TYPE int;
DEFINE FIELD doctype  ON pipeline_stage TYPE string;
DEFINE FIELD action   ON pipeline_stage TYPE string;

-- Domain nodes (reusable logic units)
DEFINE TABLE pipeline_node SCHEMAFULL;
DEFINE FIELD name     ON pipeline_node TYPE string;
DEFINE FIELD fn_name  ON pipeline_node TYPE string;
DEFINE FIELD order    ON pipeline_node TYPE int;
DEFINE FIELD doctype  ON pipeline_node TYPE string;

-- Edge: stage contains domain nodes
DEFINE TABLE has_node SCHEMAFULL;
DEFINE FIELD in      ON has_node TYPE record<pipeline_stage>;
DEFINE FIELD out     ON has_node TYPE record<pipeline_node>;
DEFINE FIELD order   ON has_node TYPE int;
DEFINE FIELD config  ON has_node TYPE option<object>;

-- Cascade rules for cancellation propagation
DEFINE TABLE cascade_rule SCHEMAFULL;
DEFINE FIELD parent_doctype  ON cascade_rule TYPE string;
DEFINE FIELD child_doctype   ON cascade_rule TYPE string;
DEFINE FIELD find_by_field   ON cascade_rule TYPE string;

-- Execution log
DEFINE TABLE pipeline_run SCHEMAFULL;
DEFINE FIELD doc         ON pipeline_run TYPE record;
DEFINE FIELD doctype     ON pipeline_run TYPE string;
DEFINE FIELD action      ON pipeline_run TYPE string;
DEFINE FIELD status      ON pipeline_run TYPE string;
DEFINE FIELD failed_node ON pipeline_run TYPE option<string>;
DEFINE FIELD errors      ON pipeline_run TYPE array<string>;
DEFINE FIELD started_at  ON pipeline_run TYPE datetime;
DEFINE FIELD finished_at ON pipeline_run TYPE option<datetime>;
```

### 1.3 — The Runner (`framework/02_runner.surql`)

Key behavior: returns `{ status: "skipped" }` instead of throwing when no pipeline is registered. This is the **progressive opt-in** mechanism — unwired doctypes fall back to the plain UPSERT path in Rust without needing a separate pre-check round-trip.

`pipeline_run` audit is handled by the Rust caller, not inside the function, because SurrealDB function transactions roll back all mutations (including audit inserts) on THROW.

```surql
DEFINE FUNCTION OVERWRITE fn::pipeline::run(
    $doc_id:  record,
    $doctype: string,
    $action:  string
) {
    LET $meta = (SELECT is_submittable FROM doctype_meta WHERE name = $doctype LIMIT 1)[0];

    -- No registration → skip (progressive opt-in; Rust falls back to plain UPSERT)
    IF $meta = NONE {
        RETURN { status: "skipped", reason: "no_pipeline" };
    };

    IF $action IN ["submit", "cancel", "amend"] AND !$meta.is_submittable {
        THROW string::concat($doctype, " is not submittable. Action '", $action, "' is not allowed.");
    };

    LET $stages = (
        SELECT id, name, ord FROM pipeline_stage
        WHERE doctype = $doctype AND action = $action
        ORDER BY ord ASC
    );

    IF array::len($stages) = 0 {
        RETURN { status: "skipped", reason: "no_stages" };
    };

    FOR $stage IN $stages {
        -- Query has_node relation table directly (supports ORDER BY)
        LET $edges = (
            SELECT out, ord, config FROM has_node
            WHERE in = $stage.id
            ORDER BY ord ASC
        );

        FOR $edge IN $edges {
            LET $node   = (SELECT fn_name FROM $edge.out)[0];
            LET $result = fn::registry::dispatch($node.fn_name, $doc_id, $edge.config OR {});

            IF type::is::object($result) AND $result.error != NONE {
                THROW string::concat("[", $node.fn_name, "] ", $result.error);
            };
        };
    };

    IF $action = "cancel" {
        fn::pipeline::cascade_cancel($doc_id, $doctype);
    };

    RETURN { status: "ok" };
};

DEFINE FUNCTION OVERWRITE fn::pipeline::cascade_cancel($doc_id: record, $doctype: string) {
    LET $rules = (SELECT * FROM cascade_rule WHERE parent_doctype = $doctype);

    FOR $rule IN $rules {
        LET $table = type::table($doc_id);
        LET $dependents = (
            SELECT id FROM type::table($rule.child_doctype)
            WHERE record::id($rule.find_by_field) = record::id($doc_id)
              AND docstatus != 2
        );

        FOR $dep IN $dependents {
            fn::pipeline::run($dep.id, $rule.child_doctype, "cancel");
        };
    };
};
```

### 1.4 — Domain Function Contract

Every domain function must return one of two shapes — never throws, never undeclared side effects:

```surql
{ ok: true }
{ error: "Human-readable error message" }
```

### 1.5 — `registry.surql` — Generated, Never Hand-Edited

SurrealDB cannot call a `fn::` by a runtime string. The registry is a generated `IF/ELSE` chain:

```surql
DEFINE FUNCTION fn::registry::dispatch(
    $fn_name: string,
    $doc_id:  record,
    $config:  object
) {
    IF $fn_name = "fn::validate::mandatory_fields" {
        RETURN fn::validate::mandatory_fields($doc_id, $config);
    } ELSE IF $fn_name = "fn::validate::party_check" {
        RETURN fn::validate::party_check($doc_id, $config);
    } ELSE IF $fn_name = "fn::on_submit::gl_entries" {
        RETURN fn::on_submit::gl_entries($doc_id, $config);
    }
    -- ... all other fn:: entries ...
    ELSE {
        THROW string::concat("Unknown pipeline node: ", $fn_name);
    };
};
```

Generated in Rust at install time inside `install_app.rs`:

```rust
fn generate_registry_surql(fn_names: &[String]) -> String {
    let mut body = String::from(
        "DEFINE FUNCTION OVERWRITE fn::registry::dispatch(\n\
         $fn_name: string, $doc_id: record, $config: object\n) {\n"
    );
    for (i, name) in fn_names.iter().enumerate() {
        let kw = if i == 0 { "IF" } else { "ELSE IF" };
        write!(body,
            "  {kw} $fn_name = \"{name}\" {{ RETURN {name}($doc_id, $config); }}\n"
        ).unwrap();
    }
    body.push_str("  ELSE { THROW string::concat(\"Unknown pipeline node: \", $fn_name); };\n};");
    body
}
```

Triggered by scanning all `.surql` files for lines matching `DEFINE FUNCTION fn::`.

## Phase 2 — Rust Save Handler → One-Line Proxy

### 2.1 — `save_proxy.rs` change (additive — existing paths unchanged)

After the existing DB write (steps 1–5 unchanged), add step 6: call `fn::pipeline::run`. The runner's `{ status: "skipped" }` return value activates the fallback transparently. No existing codepaths break.

```rust
// Step 6 (NEW): Pipeline — SurrealDB owns validation + compute for wired doctypes.
// skipped → runner returned { status: "skipped" } → keep the already-written result.
// ok      → pipeline ran; re-read the doc to capture compute mutations.
// Err     → validation/logic failure; for new docs, delete the shell and propagate.
let table = doctype_to_table(doctype);
let doc_name = /* name of the written doc */;
let rows = adapter.run(
    "RETURN fn::pipeline::run(type::thing($table, $name), $doctype, $action)",
    vec![
        ("table".into(), json!(table)),
        ("name".into(), json!(doc_name)),
        ("doctype".into(), json!(doctype)),
        ("action".into(), json!("save")),
    ]
).await;
match rows {
    Ok(ref v) if pipeline_status(v) == "ok" => {
        // Re-read: compute stage may have mutated fields
        let refreshed = get_doc(adapter, doctype, &doc_name).await
            .map(|d| d.as_dict())
            .unwrap_or(saved_doc.clone());
        return Ok(refreshed);
    }
    Ok(_) => { /* skipped — return saved_doc as-is */ }
    Err(e) if is_new => {
        // Clean up shell on pipeline failure
        let _ = adapter.execute(
            "DELETE type::record($table, $name)",
            vec![("table".into(), json!(table)), ("name".into(), json!(doc_name))]
        ).await;
        return Err(SaveProxyError::Pipeline(e.to_string()));
    }
    Err(e) => return Err(SaveProxyError::Pipeline(e.to_string())),
}
```

Same pattern added to `submit_doc_proxy` (action `"submit"`) and `cancel_doc_proxy` (action `"cancel"`).

### 2.2 — `hooks.rs` fate

Kept as a stub for **Tier 0 DocTypes only** (User, Role, DocType, DocField, DocPerm — bootstrapped before SurrealDB events exist). For all runtime-seeded types, pipeline handles the hook equivalent via `on_submit`/`on_cancel` stages.

## Phase 3 — Naming Stays in Rust

The pipeline takes a `record` type as `$doc_id` — the document must exist as a record (even a shell) before traversal begins. Naming is always resolved in Rust first.

Naming strategies (existing `naming.rs`):
- Expression-based (e.g. `PINV-.YYYY.-.#####`)
- By-fieldname
- Naming series (atomic DB counter)
- UUID fallback

**Critical sequence for new documents:**
```
Rust: auth → naming → INSERT shell → fn::pipeline::run("save")
SurrealDB: pipeline fetches the shell doc, validates, computes, updates in-place
```

## Phase 5 — Domain Function Library (Priority Order)

The framework is **progressive opt-in**. A doctype without wiring falls back to the existing direct-upsert path. Priority for wiring:

- `gl_entry` — self-validates on every write via `DEFINE FIELD ASSERT`. Cancel: mark cancelled.

- `payment_entry` — submit: GL + outstanding update. Cancel: cascade.

### Tier B — Trading Cycle
- `purchase_invoice` — full worked example from the framework paper.
- `sales_invoice`
- `purchase_order` / `sales_order`

### Tier C — Master Data
- `account` — parent validation via graph traversal (replaces `lft/rgt`), root_type computation.
- `supplier`, `customer`, `item`

### Tier D — Remaining ~470 DocTypes
Wired progressively. Each requires only `meta.surql` + `wiring.surql` + `functions/` directory. No existing files touched.

## Phase 6 — Account Tree: Nested Set → Graph Edges

Remove `lft`/`rgt` from Account. Replace with a `child_of` relation table.

```surql
-- 1. Define the relation table
DEFINE TABLE child_of SCHEMAFULL;
DEFINE FIELD in  ON child_of TYPE record<account>;
DEFINE FIELD out ON child_of TYPE record<account>;

-- 2. Seed edges from existing parent_account field (run once at migration)
FOR $acc IN (SELECT id, parent_account FROM account WHERE parent_account != NONE) {
    RELATE type::thing('account', $acc.id)
        -> child_of
        -> type::thing('account', $acc.parent_account);
};

-- 3. Ancestors query — replaces lft/rgt walk
SELECT <-child_of<-account... AS ancestors FROM account:1001;
```

SurrealQL domain function replacing `account.py::validate_parent()`:

```surql
DEFINE FUNCTION fn::validate::account_parent_check($doc_id: record, $config: object) {
    LET $doc = (SELECT parent_account, root_type FROM $doc_id)[0];
    IF $doc.parent_account {
        LET $parent = (SELECT root_type, is_group FROM account WHERE id = $doc.parent_account)[0];
        IF !$parent          { RETURN { error: "Parent account does not exist" }; };
        IF !$parent.is_group { RETURN { error: "Parent must be a group account" }; };
        IF $parent.root_type != $doc.root_type {
            RETURN { error: "Root type must match parent's root type" };
        };
    };
    RETURN { ok: true };
};
```

Rust change: remove `lft`/`rgt` from Account DocType JSON in `apps/erpnext/`.

## Phase 7 — Metadata Graph + Pipeline Graph Unified View

Both graphs live in SurrealDB simultaneously. A complete picture of any doctype is one multi-hop query:

```surql
SELECT
    (SELECT ->has_field->docfield.* FROM doctype:purchase_invoice) AS fields,
    (SELECT * FROM pipeline_stage
     WHERE doctype = "purchase_invoice" ORDER BY action, order) AS stages,
    (SELECT ->has_node->pipeline_node.fn_name, ->has_node.config
     FROM pipeline_stage WHERE doctype = "purchase_invoice") AS nodes,
    (SELECT * FROM cascade_rule WHERE parent_doctype = "purchase_invoice") AS cascades
;
```

The metadata graph (`doctype`/`docfield`) answers "what data does this type have."  
The pipeline graph (`pipeline_stage`/`pipeline_node`/`has_node`) answers "what happens when you save/submit/cancel it."  
They are separate subgraphs in the same SurrealDB instance, linked by the `doctype` string key on `pipeline_stage`.

## Phase 9 — Querying the Pipeline Graph

Because topology lives in the database as records and edges, you can query it directly:

```surql
-- What stages run when purchase_invoice is submitted?
SELECT name, order FROM pipeline_stage
WHERE doctype = "purchase_invoice" AND action = "submit"
ORDER BY order ASC;

-- What nodes run in the validate stage for purchase_invoice submit?
SELECT ->has_node->pipeline_node.fn_name AS fn, ->has_node.order AS order,
       ->has_node.config AS config
FROM pipeline_stage
WHERE doctype = "purchase_invoice" AND action = "submit" AND name = "validate"
ORDER BY ->has_node.order ASC;

-- Which doctypes use fn::validate::party_check?
SELECT <-has_node<-pipeline_stage.doctype AS doctype, <-has_node.config AS config
FROM pipeline_node
WHERE fn_name = "fn::validate::party_check";

-- All failed runs in the last 24 hours
SELECT doc, doctype, action, failed_node, errors, started_at
FROM pipeline_run
WHERE status = "failed" AND started_at > time::now() - 24h
ORDER BY started_at DESC;

-- Full execution history for a specific document
SELECT action, status, failed_node, errors, started_at, finished_at
FROM pipeline_run
WHERE doc = purchase_invoice:PINV-2025-00001
ORDER BY started_at ASC;
```

## Invariants That Cannot Change

1. **Naming happens in Rust before `fn::pipeline::run`** — the doc must exist as a record before traversal begins (runner takes a `record` type as `$doc_id`).
2. **Auth happens in Rust** — SurrealDB's table-level permission model cannot encode Frappe's role + doctype + user-permission matrix.
3. **Domain functions never throw, never have undeclared side effects** — only the runner throws, only after recording the failure in `pipeline_run`.
4. **`registry.surql` is always generated** — never hand-edited. Scan → generate → apply at install time.
5. **Tier 0 types bypass the pipeline** — DocType, DocField, DocPerm, User, Role use the compiled Rust controller. The pipeline is for runtime-seeded types only.
6. **Every `fn::` must be in `registry.surql`** — the codegen enforces this; any unknown `fn_name` at runtime throws immediately from the dispatcher.
7. **Submit always re-validates** — the gap between save and submit may be minutes or days; trusting saved state is unsound.
8. **Cancellation is recursive, not reversal** — Purchase Invoice cancel does not contain GL reversal logic; it triggers `fn::pipeline::run` on each dependent `gl_entry`, which defines its own cancel behaviour.

## Design Principles

**Fail-fast, always.** The first domain function that returns `{ error: "..." }` halts the entire traversal. No partial state is committed.

**Submit always re-validates.** Every submit re-runs validate and compute from scratch.

**Cancellation is recursive, not reversal.** Each document type defines its own cancel behaviour. The framework is the recursion mechanism.

**Nodes are universal, edges carry context.** A domain function never hardcodes a doctype-specific field name. Context that varies across doctypes is encoded on the `has_node` edge as a `config` object.

**The graph is the documentation.** Pipeline topology is stored as queryable records and edges. "What happens when this doctype is submitted?" is a database query, not a code archaeology expedition.

**Nodes are global, wiring is per-doctype.** `fn::validate::party_check` is created once and shared. Adding it to a new doctype is a `RELATE` operation, not a code change.
